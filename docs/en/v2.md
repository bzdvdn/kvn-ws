# KVN v2 — TCP-first stealth transport

KVN v2 is the only protocol in 2.0.0 and is **not wire-compatible with v1**. Old v1 builds are available only in GitHub Releases and are not part of the current tree.

## Architecture

- TLS 1.3 + HTTP/2.
- TCP flows are terminated on the client by gVisor netstack and carried as individual HTTP/2 streams.
- The server opens normal TCP sockets to the target; no userspace TCP stack is needed on the server.
- UDP uses best-effort HTTP/2 streams by default.
- With `quic_enabled: true`, UDP uses **one shared QUIC connection**: datagrams carry a flow ID, with no per-flow stream/channel. If QUIC is unavailable, the client falls back to HTTP/2 UDP.
- Bearer is checked before the stream; invalid requests get the fallback site.
- One HTTP/2 client is reused for all flows; no TLS connection per flow.

## Server

```yaml
listen: 0.0.0.0:443
tls:
  cert: /etc/kvn-ws/certs/server.pem
  key: /etc/kvn-ws/certs/server-key.pem
auth:
  tokens:
    - name: default
      secret: change-me
fallback:
  title: Acme Telemetry
  # upstream: https://real-site.example
max_streams: 512   # for 1 CPU / 1–2 GB
```

Run:

```bash
./bin/kvn-server --config configs/server.yaml
```

## Client: standalone or kvn-web

`kvn-client` is a fully supported standalone entrypoint: a config plus the binary is enough. kvn-web is an optional UI that runs the same v2 client in-process.

1. Run `kvn-web` as root (TUN/routes/resolv.conf).
2. Add server:
   - Server URL: `https://host:443`
   - Token
   - Mode: `tun`
   - TUN Address: `10.66.0.2/24`
   - TUN Gateway: `10.66.0.1`
3. Routing/DNS/TLS live in dedicated tabs.
4. Connect.

`kvn-web` is the only UI in 2.0.0 and it is v2-only. Settings live in `~/.config/kvn/config.yaml`; the v1 `config.yaml` is neither read nor written (except a one-time import of entries marked `protocol: v2`). v1 is available only in old releases.

CLI diagnostics:

```bash
sudo ./bin/kvn-client --config configs/client.yaml
```

## Android 2.0: chosen path

- The Go v2 data plane compiles for `android/arm64` and `android/amd64` with `CGO_ENABLED=0`; gVisor/TCP stack needs no protocol change.
- Recommended path: `gomobile bind` the shared Go core (`src/mobile`) + a `VpnService` fd from Kotlin. Kotlin configures TUN/routes/DNS; Go reads/writes the fd and owns v2 HTTP/2/QUIC.
- DNS routing/fake-DNS/direct delivery stay on the Kotlin side; the v2 core must not duplicate them.
- Android QUIC-UDP is not required for the 2.0 MVP; v2 HTTP/2 UDP fallback is used, QUIC can follow after TCP/TUN.
- AAR environment: Android SDK + **NDK 28.x** + `gomobile`; NDK 28.2 is installed, and gomobile/AAR is the next step.

### TUN assignment

The server assigns a unique `tun_address` from its pool and a shared `tun_gateway`. The client has no local TUN fields and does not start TUN when assignment is unavailable.

```yaml
tun:
  subnet: 10.66.0.0/24
  range_start: 10.66.0.2
  range_end: 10.66.0.254
  gateway: 10.66.0.1
  lease_ttl_sec: 300
```

## QUIC datagrams for UDP

QUIC is one shared channel per client for all UDP flows. Each datagram carries a flow ID; the server keeps one UDP socket per flow. This is a QUIC datagram side channel with ALPN `h3`, not full HTTP/3 framing.

```yaml
quic_enabled: true
quic_endpoint: vpn.example.com:8443
mtu: 1200   # keep UDP payloads inside the QUIC datagram budget
```

Server:

```yaml
quic_listen: 0.0.0.0:8443
```

If QUIC is blocked, the client falls back to HTTP/2 UDP streams.

## Split tunnel

- `routing.exclude_ranges`/`exclude_ips` become OS exclude routes.
- `routing.exclude_domains` are handled by the DNS proxy: direct domains resolve directly and get an exclude route.
- DNS upstream currently goes direct (outside the VPN).

## Limitations

- v2 is not wire-compatible with v1.
- ICMP echo (`ping`) is supported through the server ICMP proxy; `traceroute` and other ICMP types may not work.
- UDP is best-effort over HTTP/2/TCP; H3 datagrams for video/voice are not implemented yet.
- TUN requires root/CAP_NET_ADMIN.
- gVisor runs on the client; the server has no userspace TCP stack.
- On 1 CPU / 1–2 GB set `max_streams: 256–512`; TLS/HTTP2 CPU is the bottleneck, not RAM.
- Relay v2, Android v2 and H3 are separate phases.
