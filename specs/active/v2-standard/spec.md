# v2 как эталонный релиз

## Scope Snapshot

- In scope: выпустить 2.0.0 как v2-only релиз, удалить v1 из кодовой базы и сборки, сделать `kvn-web` только v2, перевести Android-клиент на v2, включить stealth/uTLS по умолчанию и добавить DPI-гейт.
- Out of scope: изменение v2 wire-формата, relay-режим, поддержка исходников v1 в текущем дереве и гарантия обхода конкретного DPI-вендора.

## Цель

Релиз 2.0.0 даёт пользователю только v2: `kvn-web` без v1-полей, отдельный `config.yaml`, v2-only сервер/клиент, переработанный Android-клиент и stealth-профиль по умолчанию. Исходники v1 удаляются из текущего дерева; старые v1-релизы остаются доступны в разделе релизов и документируются как legacy. Перед релизом DPI-проверка подтверждает, что v2 не оставляет явных KVN-отпечатков и умеет отдавать fallback.

## Основной сценарий

1. Пользователь устанавливает 2.0.0 и запускает `kvn-web` или Android-клиент.
2. UI показывает только v2-серверы и только применимые к v2 настройки; сохранение пишет в `~/.config/kvn/config.yaml`.
3. Пользователь подключается, проверяет YouTube/скачивание и видит работоспособный v2-туннель; по умолчанию клиент представляется браузерным TLS/HTTP2-профилем.
4. DPI/active-probe проверка не находит KVN-специфичных заголовков/путей, а подозрительный запрос получает fallback-сайт.
5. Если нужен v1, пользователь скачивает старый v1-релиз из раздела релизов; в 2.0.0 v1-кода и v1-переключателя уже нет.

## User Stories

- P1: как новый пользователь, я вижу v2 как основной продукт и не разбираюсь с v1-полями, которые v2 не использует.
- P2: как Android-пользователь, я подключаюсь через v2 и не вижу v1-engine.
- P3: как мейнтейнер, я работаю в одной v2-кодовой базе, а v1 остаётся только в старых релизах и документации.

## MVP Slice

- v2-only UI и изолированный `config.yaml`.
- Удаление v1 из сборки и текущего дерева.
- v2-only Android-клиент.
- uTLS/браузерный TLS-профиль и stealth-режим по умолчанию.
- DPI-гейт перед релизом.
- Документация и карта репозитория, отражающие 2.0.0.
- Закрывает `AC-001`–`AC-011`.

## First Deployable Outcome

- Можно запустить `kvn-web`, создать v2-сервер, подключиться и убедиться, что v1 `config.yaml` не изменён.
- Android-клиент подключается к тому же v2-серверу.
- По умолчанию v2-клиент использует uTLS-профиль браузера и stealth-заголовки; DPI-проверка и fallback воспроизводимы.
- В сборке 2.0.0 нет v1-бинарей; инструкция по скачиванию v1 ведёт на старые релизы.

## Scope

- v2-only web UI, серверный API и хранилище настроек.
- Удаление v1-кода, entrypoint'ов, бинарей и v1-веток UI из текущего дерева.
- Android-клиент на v2: подключение, TUN, конфиг, UI без v1-engine.
- uTLS/ClientHello-профиль, браузерные HTTP/2-заголовки, отсутствие KVN-специфичных путей/заголовков и fallback по умолчанию.
- DPI/active-probe проверка и воспроизводимый отчёт до 2.0.0.
- Основные entrypoints/бинарники и build/release-скрипты 2.0.0.
- README/CHANGELOG/docs, `REPOSITORY_MAP.md` и `CONTEXT.md` затронутых модулей.
- Тесты и CI-проверки, доказывающие, что v1 больше не собирается, а v2-контуры работают.

## Контекст

- Текущий опубликованный релиз — v1.4.1; 2.0.0 — следующий мажорный релиз.
- v1 и v2 несовместимы по wire-протоколу; в 2.0.0 остаётся только v2.
- В репозитории уже есть общие config/routing/DNS/TUN/webui-пакеты; v1-поля протекают в v2 UI.
- Пользовательские конфиги v1 уже лежат в `~/.config/kvn/config.yaml`; v2 не должен их перезаписывать.
- Старые v1-бинари и инструкции остаются в GitHub Releases; исходники v1 из main-ветки удаляются.
- Android-клиент сейчас использует v1 WebSocket-транспорт и требует переработки на v2.
- В Android уже есть DNS routing/fake-DNS (`FakeDnsResolver`, `FakeIpPool`, `DirectDeliverer`); QUIC-транспорта на Android сейчас нет.

## Зависимости

- Существующий v2 transport/client/server и v2-only web UI.
- Android-приложение и его текущий VPN/TUN-слой.
- TLS-стек клиента (`crypto/tls`/uTLS) и HTTP/2-транспорт.
- DPI/active-probe инструменты и тестовый стенд.
- `REPOSITORY_MAP.md` и модульные `CONTEXT.md` как источник навигации.
- GitHub Releases как место хранения старых v1-артефактов.

## Требования

- RQ-001 Релиз 2.0.0 ДОЛЖЕН содержать только v2-код, v2-бинари и v2-UI; v1-исходники и v1-entrypoint'ы удаляются из текущего дерева.
- RQ-002 `kvn-web` ДОЛЖЕН быть v2-only и показывать только v2-серверы и применимые к v2 настройки.
- RQ-003 v2 UI ДОЛЖЕН хранить серверы и глобальные настройки в едином `~/.config/kvn/config.yaml`.
- RQ-004 При первом запуске старый v1 `config.yaml` ДОЛЖЕН сохраняться как `config.yaml.v1.bak`, а старый `v2/config.yaml` — мигрировать в единый `config.yaml`.
- RQ-005 Существующие v2-записи из общего конфига ДОЛЖНЫ без потери попадать в v2-хранилище при первом запуске.
- RQ-006 Android-клиент ДОЛЖЕН использовать v2-транспорт и не содержать v1-engine/переключателя.
- RQ-007 Build/release-артефакты 2.0.0 ДОЛЖНЫ собирать только v2-контуры; v1-артефакты доступны только в старых релизах.
- RQ-008 Документация ДОЛЖНА описывать v2 как эталон, а v1 — только как скачиваемый legacy-релиз с примерами.
- RQ-008a В 2.0.0 ДОЛЖЕН поставляться только `kvn-web` как v2-only; отдельного `kvn-web-v2` алиаса нет.
- RQ-009 `REPOSITORY_MAP.md` и `CONTEXT.md` затронутых модулей ДОЛЖНЫ отражать v2-only структуру.
- RQ-010 v2-клиент ДОЛЖЕН поддерживать несколько браузерных uTLS-профилей (Chrome/Firefox/Safari), выбирать один по умолчанию и иметь fallback на стандартный TLS.
- RQ-011 v2-трафик ДОЛЖЕН по умолчанию выглядеть как браузерный HTTPS/HTTP2: без KVN-специфичных путей, заголовков и отличимых握手-паттернов; подозрительные запросы получают fallback.
- RQ-012 До релиза 2.0.0 ДОЛЖЕН быть воспроизводимый DPI/active-probe прогон, доказывающий отсутствие явных KVN-отпечатков и работоспособность fallback.
- RQ-013 Android-клиент ДОЛЖЕН сохранить существующий DNS routing/fake-DNS и direct-delivery при переходе на v2; UDP без QUIC должен работать через v2 HTTP/2 fallback.

## Вне scope

- Изменение v2 wire-формата, QUIC/H2-алгоритмов и производительности.
- Relay-режим и серверная миграция v1→v2.
- Сохранение исходников v1 в текущем дереве.
- Перевыпуск TLS-сертификатов и настройка PKI.
- Гарантированный обход конкретного DPI-вендора или страны; проверяется отсутствие явных отпечатков, а не обещание обхода.

## Критерии приемки

### AC-001 2.0.0 — только v2

- Почему важно: пользователь не должен выбирать experimental-режим или отдельный v2-бинарь, чтобы получить актуальный продукт.
- **Given** чистый релиз 2.0.0 без пользовательских конфигов
- **When** пользователь запускает `kvn-web`
- **Then** открывается v2-контур; v1-кода, v1-бинарей, `kvn-web-v2` и v1-переключателя в релизе нет
- Evidence: список артефактов 2.0.0 и `--help`/README не содержат v1 entrypoint'ов или `kvn-web-v2`.

### AC-002 `kvn-web` не показывает v1-поля

- Почему важно: v1-настройки в v2 UI вводят в заблуждение и ломают конфиг при переключении.
- **Given** запущен `kvn-web` из 2.0.0
- **When** пользователь открывает настройки сервера
- **Then** нет protocol selector, transport/obfuscation/multiplex/crypto/dual-channel и других v1-only контролов; отображаются только v2-поля, включая выбор uTLS-профиля
- Evidence: UI-тест или ручная проверка DOM; v2-конфиг не содержит v1-only значений.

### AC-003 v2 пишет только в свой конфиг

- Почему важно: v1-конфиг пользователя не должен меняться при работе с v2.
- **Given** существует `~/.config/kvn/config.yaml` с v1-серверами
- **When** пользователь создаёт/меняет v2-сервер и сохраняет глобальные настройки
- **Then** изменения появляются в `~/.config/kvn/config.yaml`, а старый v1-файл сохранён как `config.yaml.v1.bak`
- Evidence: тест `TestV2StoreIsolation` и diff backup-файла.

### AC-004 v1 удалён из текущего дерева

- Почему важно: 2.0.0 должен оставить одну кодовую базу, а не два параллельных контура.
- **Given** исходники и build-скрипты 2.0.0
- **When** запускается release-сборка
- **Then** v1 client/server/web UI не собираются и не входят в артефакты; v1-код отсутствует в текущем дереве
- Evidence: `git ls-files`/build output не содержат v1 entrypoint'ов и v1-бинарей.

### AC-005 Старые v2-записи мигрируют

- Почему важно: текущие тестеры v2 не должны потерять серверы после разделения конфигов.
- **Given** в общем `config.yaml` есть записи с `protocol: v2`
- **When** впервые запускается `kvn-web`
- **Then** эти записи доступны в v2 UI и сохранены в v2-хранилище, а v1-записи не скопированы и не изменены
- Evidence: тест миграции `TestV2StoreMigratesOnlyV2Entries`.

### AC-006 v1 доступен как старый релиз

- Почему важно: пользователи, которым нужен v1, должны найти его без возврата v1-кода в main.
- **Given** опубликован 2.0.0
- **When** пользователь открывает документацию и раздел релизов
- **Then** там есть инструкция скачать/запустить v1-релиз и примеры его конфигурации, но нет обещания поддержки v1 в 2.0.0
- Evidence: docs/ru|en и ссылки на GitHub Releases; v1-бинари отсутствуют в 2.0.0.

### AC-007 Android-клиент работает через v2

- Почему важно: 2.0.0 должен быть единым v2-релизом на всех платформах.
- **Given** Android-клиент из 2.0.0 и настроенный v2-сервер
- **When** пользователь подключается и открывает YouTube/скачивание
- **Then** трафик идёт через v2-транспорт, в UI нет v1-engine/переключателя, TUN работает, а DNS routing/fake-DNS и direct-delivery сохраняют прежнее поведение
- Evidence: Android integration/e2e-тест или воспроизводимая ручная проверка с логами v2-соединения и DNS-routing.

### AC-008 Навигационная документация обновлена

- Почему важно: новый контур должен быть понятен без чтения исходников.
- **Given** завершён переход на v2-эталон
- **When** разработчик открывает `REPOSITORY_MAP.md` и `CONTEXT.md` затронутых модулей
- **Then** v2-модули и entrypoints описаны как основные, v1 упомянут только как старый релиз
- Evidence: обновлённые файлы и ссылки на них в README/docs.

### AC-009 DPI/active-probe гейт

- Почему важно: v2 должен быть не только производительным, но и не выдавать себя явными KVN-маркерами.
- **Given** собран v2-клиент 2.0.0 и тестовый стенд с DPI/active-probe проверками
- **When** прогоняется обязательный набор: TLS ClientHello/ALPN, HTTP/2 headers, случайные пути, active probe без токена и fallback
- **Then** отчёт не содержит KVN-специфичных путей/заголовков/ALPN-маркеров, probe получает fallback-страницу, а в отчёте записаны сеть и регион прогона
- Evidence: расширенный `scripts/dpi-check.sh` + active-probe отчёт с отдельного IP; reviewer воспроизводит автоматическую часть.

### AC-010 uTLS по умолчанию

- Почему важно: ClientHello — самый заметный отпечаток клиента.
- **Given** v2-клиент запущен без override-настроек
- **When** он устанавливает TLS-соединение
- **Then** ClientHello соответствует выбранному браузерному uTLS-профилю, доступен выбор минимум из нескольких профилей, ALPN содержит `h2`, а при ошибке uTLS клиент откатывается на стандартный TLS без падения
- Evidence: тест ClientHello/ALPN для нескольких профилей и лог fallback-пути.

### AC-011 Stealth по умолчанию

- Почему важно: пользователь не должен включать скрытность вручную.
- **Given** чистый v2-конфиг
- **When** пользователь подключается
- **Then** используются браузерные HTTP/2-заголовки и fallback, KVN-специфичные заголовки/пути не отправляются; явное отключение stealth возможно только отдельной настройкой
- Evidence: конфиг по умолчанию, перехваченные заголовки и active-probe ответ.

## Допущения

- Следующий релиз — `2.0.0`; v1.4.1 остаётся опубликованным и не переписывается.
- v1 удаляется из текущего дерева; старые v1-артефакты и примеры остаются в GitHub Releases и документации.
- `kvn-web` в 2.0.0 — единственный web-бинарь и он v2-only; `kvn-web-v2` не поставляется.
- Android-клиент должен быть переведён на v2 в рамках 2.0.0; существующий DNS routing/fake-DNS сохраняется, а QUIC-UDP не считается обязательным без отдельного решения.
- Базовый Android v2 MVP использует TUN/TCP и HTTP/2 UDP fallback; QUIC-UDP можно добавить после него.
- Поддерживается несколько актуальных браузерных uTLS-профилей; один выбран по умолчанию, остальные доступны в конфиге.
- Несколько профилей означают выбор ClientHello-паттерна, а не одновременную ротацию внутри одного соединения.
- uTLS имеет fallback на стандартный TLS.
- «Stealth по умолчанию» означает браузерный TLS/HTTP2-профиль и fallback, а не гарантию обхода любого DPI.
- Обязательный DPI-гейт двухуровневый: автоматический локальный/CI-набор без привязки к стране + один реальный целевой регион/сеть, выбранный release owner и записанный в отчёте. Страна не хардкодится в коде.
- Если полевой прогон в целевом регионе недоступен, релиз может заявлять только отсутствие явных отпечатков, но не «обходит DPI».
- Пользователь запускает web UI локально и имеет права root/CAP_NET_ADMIN для TUN.
- Конфиг v2 может быть создан с нуля; пустой v2-конфиг — валидное first-run состояние.

## Критерии успеха

- SC-001 v2 UI не пишет в v1 `config.yaml` ни при create, ни при update, ни при global save.
- SC-002 В release-артефактах 2.0.0 нет v1-бинарей и v1-entrypoint'ов.
- SC-003 DPI-гейт воспроизводится одной командой и не требует ручной настройки DPI-стенда.
- SC-004 uTLS + stealth не добавляют заметной деградации скорости относительно текущего v2 (в пределах согласованного допуска).

## Краевые случаи

- `config.yaml` отсутствует или пуст — v2 UI стартует с пустым списком и позволяет добавить сервер.
- В v1-конфиге нет v2-записей — миграция ничего не создаёт.
- v1-конфиг отсутствует — v2 UI не создаёт v1-файл.
- Пользователь удаляет последний v2-сервер — операция отклоняется.
- У пользователя остался старый v1-конфиг — v2 его не читает и не перезаписывает; v1 запускается из старого релиза.
- Android-пользователь обновляется с v1-приложения — новая версия не предлагает v1-engine.
