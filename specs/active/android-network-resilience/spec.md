# Android: устойчивость сетевого жизненного цикла

## Scope Snapshot

- In scope: Android-клиент корректно переживает смену underlying-сети, блокировку экрана, недоступный QUIC и пользовательские DNS-настройки; жизненный цикл сессии не оставляет зависших/лишних реконнектов и соединений.
- Out of scope: удаление легаси-Kotlin транспорта/протокола, изменения серверного протокола, переработка split-tunnel сверх исключения собственного процесса, оптимизация батареи latency-пробы.

## Цель

Пользователь Android-клиента перестаёт видеть ложные обрывы и «залипания» при переключении Wi-Fi/LTE, разблокировке экрана, включённом QUIC и собственных DNS-настройках. Сессия пересоздаётся только при реальной смене сети или нездоровом транспорте, старт укладывается в ограниченное время, а настройки DNS применяются. Успех виден по отсутствию reconnect-шторма, стабильному статусу в UI и корректной работе direct-доменов.

## Основной сценарий

1. Пользователь подключается; VpnService поднимает TUN, Go-ядро обслуживает трафик.
2. При появлении/исчезновении underlying-сетей клиент обновляет привязку и пересоздаёт сессию только при фактической смене активной сети.
3. При разблокировке экрана здоровая сессия продолжает работать; нездоровая — восстанавливается.
4. Если QUIC-эндпоинт недоступен, старт за ограниченное время откатывается на HTTP/2 UDP, не блокируя packet pump.
5. Пользовательские DNS-серверы применяются в VpnService; резолв direct-доменов не уходит повторно в туннель.
6. Остановка/перезапуск освобождает транспортные соединения и не оставляет конкурентных рестартов.

## User Stories

- P1 Story: как пользователь, я могу переключаться между Wi-Fi и мобильной сетью без reconnect-шторма.
- P1 Story: как пользователь, я могу разблокировать телефон, не теряя рабочее соединение.
- P2 Story: как пользователь с включённым QUIC, я не жду долгий старт при блокировке UDP.
- P2 Story: как пользователь, я ожидаю, что заданные DNS-серверы реально используются.
- P2 Story: как пользователь, я могу переподключиться с новым конфигом без «вечного Connecting».

## MVP Slice

Наименьший срез: AC-001 (нет reconnect-шторма) и AC-003 (bounded QUIC-старт) — они дают основной эффект «сеть не дёргается и не висит на старте».

## First Deployable Outcome

Debug APK, в котором при двух доступных сетях нет повторных реконнектов, а при blackhole-UDP старт укладывается в несколько секунд. Проверяется Kotlin unit-тестами решения и Go-тестом bounded QUIC.

## Scope

- Логика реакции на `onAvailable`/`onLost` и выбор активной underlying-сети.
- Поведение при `ACTION_USER_PRESENT` в зависимости от здоровья сессии.
- Ограниченный handshake QUIC и fallback на HTTP/2 UDP.
- Применение пользовательских DNS-серверов в VpnService и исключение собственного процесса из VPN.
- Single-flight restart и применение нового конфига при повторном старте.
- Закрытие idle-соединений транспорта при завершении сессии; ограничение конкурентных ICMP-пингов.

## Контекст

- Android VpnService владеет TUN fd; Go не закрывает чужой дескриптор.
- VpnService поддерживает одновременно include- и exclude-списки, если пакет не входит в оба.
- `ConnectionConfig.dnsServers` уже передаётся в v2 JSON как `dns_proxy.upstreams`.
- `transport.Client` переиспользует HTTP/2-соединение; при пересоздании сессии старые idle-соединения должны закрываться.
- Должно сохраниться поведение: split-tunnel, direct-маршрутизация, fallback при недоступном QUIC.

## Зависимости

- quic-go (настройки handshake timeout).
- Android ConnectivityManager network callbacks и VpnService.Builder.
- `src/mobile` AAR-контракт между Kotlin и Go.

## Требования

- RQ-001 Клиент пересоздаёт сессию только при фактической смене активной underlying-сети; лишние `onAvailable` не вызывают рестарт.
- RQ-002 Разблокировка экрана не прерывает здоровую сессию и инициирует восстановление только для нездоровой.
- RQ-003 Старт с включённым QUIC при недоступном UDP откатывается на HTTP/2 UDP за ограниченное время.
- RQ-004 VpnService использует DNS-серверы из конфигурации пользователя, а собственный процесс исключён из VPN, чтобы direct-резолв не замыкался в туннель.
- RQ-005 Повторный старт с новым конфигом применяет его и всегда завершается наблюдаемым состоянием; конкурентные рестарты схлопываются в один.
- RQ-006 Завершение сессии закрывает idle-соединения транспорта; число одновременных ICMP-пингов ограничено.

## Вне scope

- Удаление легаси-Kotlin transport/protocol классов.
- Изменения серверной части, протокола и формата конфигурации.
- Переработка split-tunnel логики сверх исключения собственного процесса.
- Оптимизация 10-секундной raw-TCP latency-пробы (метрика, не влияет на зависания).
- UI-косметика и локализация.

## Критерии приемки

### AC-001 Нет reconnect-шторма при нескольких сетях

- Почему это важно: сейчас при двух доступных сетях рестарты могут идти по кругу.
- **Given** два доступных underlying-сети и работающая сессия
- **When** приходят повторные `onAvailable` без смены активной сети
- **Then** сессия не перезапускается; при фактической смене сети происходит ровно один рестарт и `setUnderlyingNetworks` указывает на новую сеть
- Evidence: unit-тесты чистой функции решения (duplicate → no-op, real change → restart once) и вызовы из сервиса.

### AC-002 Unlock не рвёт здоровую сессию

- Почему это важно: сейчас каждое разблокирование экрана пересоздаёт туннель.
- **Given** работающая здоровая сессия
- **When** приходит `ACTION_USER_PRESENT`
- **Then** рестарт не выполняется; для нездоровой сессии восстановление запускается
- Evidence: unit-тест решения unlock + проводка в `screenReceiver`.

### AC-003 QUIC-старт ограничен по времени

- Почему это важно: недоступный UDP может надолго задержать старт датаплейна.
- **Given** `quic_enabled=true`, UDP-эндпоинт принимает пакеты, но не отвечает
- **When** клиент стартует
- **Then** попытка QUIC завершается ограниченной ошибкой, и клиент переходит на HTTP/2 UDP за ≤5 с, не блокируя packet pump
- Evidence: Go-тест с blackhole UDP-сервером измеряет время возврата `NewQUICClient`/fallback.

### AC-004 Пользовательские DNS применяются

- Почему это важно: сейчас Android-клиент жёстко ставит 1.1.1.1 и игнорирует настройку.
- **Given** в `ConnectionConfig` заданы DNS-серверы
- **When** VPN поднимается
- **Then** VpnService объявляет именно эти резолверы, а собственный процесс исключён из VPN, поэтому direct-резолв не замыкается через туннель
- Evidence: unit-тест извлечения DNS из v2 JSON; код сборки VpnService.Builder.

### AC-005 Новый конфиг применяется без зависания

- Почему это важно: повторный connect при уже запущенном client оставлял UI в `CONNECTING`.
- **Given** запущенная сессия
- **When** запрошен старт с новым конфигом
- **Then** старая сессия останавливается, новая применяется, UI получает наблюдаемый state; конкурентные рестарты не выполняются параллельно
- Evidence: unit-тест single-flight гейта; проверка ветки `onStartCommand` при `client != null`.

### AC-006 Остановка освобождает ресурсы

- Почему это важно: пересоздания сессии копят idle HTTP/2-соединения и горутины пингов.
- **Given** работающая сессия
- **When** сессия завершается
- **Then** idle-соединения транспорта закрываются, а число одновременных ICMP-пингов ограничено
- Evidence: Go-тест на вызов закрытия idle-соединений и на ограничение параллельных пингов.

## Допущения

- Сервер поддерживает повторные `Session`-запросы и HTTP/2 keepalive.
- Android API уровня minSdk 26 позволяет одновременно использовать include- и exclude-списки.
- DNS-серверы в конфиге заданы как `host:port`; для VpnService берётся host.
- Blackhole UDP моделируется тестовым сервером, а не реальной сетью.
- Ограничения времени уточняются в plan/tasks.

## Критерии успеха

- SC-001 При двух доступных сетях за 60 с наблюдается ≤1 рестарт вместо цикла.
- SC-002 Старт с недоступным QUIC — ≤5 с до fallback.
- SC-003 После 10 циклов restart не остаётся открытых idle h2-соединений от прошлых сессий.

## Краевые случаи

- Все underlying-сети потеряны, затем появляется одна.
- `onAvailable` приходит для той же сети с другим handle.
- Unlock во время активного рестарта.
- DNS-конфиг пуст или содержит `host:port`.
- Повторный старт во время уже идущего рестарта.
- Остановка во время QUIC-попытки.
