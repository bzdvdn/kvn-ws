# Dual WebSocket Channel — UDP-media isolation for VoIP latency

## Scope Snapshot

- In scope: выделение UDP-трафика (голосовые звонки) в отдельный второй WebSocket-канал того же клиента/сессии, избавляющее VoIP-медиа от head-of-line blocking общего WS-потока, с сохранением единого session_id, TLS/WS-обфускации и обратной совместимости для одиночного канала.
- Out of scope: QUIC-транспорт, переделка фреймового протокола, proxy-режим (SOCKS5 UDP), Android-клиент (OkHttp), изменение схемы аутентификации.

## Цель

Пользователи kvn-web и Go-клиентов (Linux/Windows/desktop) получают стабильный голос в звонках (Telegram/WhatsApp/Discord) в TUN-режиме: UDP-медиа идёт отдельным WS-каналом и больше не стопорится ретрансмиссиями TCP-трафика в общем потоке. Успех — два WS-соединения одной сессии, UDP-пакеты не разделяют write-очередь с TCP-пакетами, все существующие тесты зелёные.

## Основной сценарий

1. Стартовая точка: Go-клиент (kvn-web или CLI) в TUN-режиме устанавливает первичный WS-канал как сегодня — handshake, сервер выдаёт `session_id`, назначенный IP, route setup.
2. Основное действие: клиент открывает вторичный WS-канал к тому же endpoint, передаёт в ClientHello `session_id` первичного канала и маркер вторичного канала; сервер находит активную сессию по `session_id` и привязывает второй стрим. Пакеты из TUN классифицируются по IP-протоколу: UDP → вторичный канал, всё остальное (TCP/ICMP) → первичный.
3. Результат: write-очереди двух каналов независимы (у каждого свой `writeMu` и свой TCP-поток), поэтому потеря/ретрай сегмента TCP-трафика не задерживает RTP-пакеты звонка.
4. Ошибка/fallback: если вторичный канал не установился (сервер не поддерживает фичу/ошибка привязки) — клиент продолжает работу на одном первичном канале со всеми пакетами (поведение сегодняшнего дня).

## User Stories

- P1 Story: Как пользователь kvn-web/Go-клиента в TUN-режиме, я хочу чтобы голосовые звонки шли отдельным каналом от остального трафика, чтобы ретраи загрузки/браузинга не «роботизировали» мой голос.
- P2 Story: Как разработчик протокола, я хочу сохранить единый `session_id` для обоих каналов, чтобы серверная привязка IP/сессии и возвратная маршрутизация (`TunDemux`) не требовали новой логики.

## MVP Slice

Первичный клиент→сервер: второй WS-канал, привязка по `session_id`, классификация UDP→secondary / остальное→primary, фоллбэк на одиночный канал. Обязательные AC для MVP: AC-001, AC-002, AC-003, AC-004, AC-005.

## First Deployable Outcome

Интеграционный сценарий `tunnel_integration_test.go`: клиент с двумя каналами, UDP-пакеты приходят на сервер через вторичный канал, TCP — через первичный; при искусственной задержке первичного канала UDP-медиа не блокируется. Одиночный канал продолжает работать без изменений конфигурации.

## Scope

- `protocol/handshake.yaml` + codegen: поля ClientHello (вторичный канал + session_id), обратная совместимость.
- `src/internal/bootstrap/client/` — dial двух стримов, последовательный handshake, фоллбэк.
- `src/internal/tunnel/session.go` — поддержка двух стримов: классификация пакетов по протоколу, независимые write-пути, буфер вторичного канала.
- `src/internal/tunnel/demux.go` — выбор стрима для возвратных пакетов по протоколу.
- `src/internal/bootstrap/server/` — приём вторичного канала, привязка к сессии по `session_id`.
- Интеграционный тест: `src/integration/`.

## Контекст

- TUN-режим оборачивает целые IP-пакеты в `FrameTypeData`; отдельного UDP-фрейм-типа нет (`protocol/frames.yaml`), разделение вводится маршрутизацией, а не новыми типами фреймов.
- Вся передача сессии сейчас идёт через один `stream StreamConn` (`session.go`), `WSConn.writeMu` сериализует все writes одного канала (`websocket.go:221-250`).
- Оба существующих WS-пути уже ставят `SetNoDelay(true)` (`websocket.go:362`, `:454`) — Nagle не является причиной HoL; причина — единственный TCP-поток на сессию.
- Обфускация (uTLS, padding, WS-фрейминг) живёт в transport-слое и не зависит от числа соединений; вторичный канал использует тот же `WSConfig`.
- Существующий `TunDemux` (`demux.go`) уже отдаёт возвратные пакеты по IP назначения в сессию — остаётся выбрать стрим по протоколу.
- Android использует OkHttp/`transport="tcp"` (`KvnVpnService.kt:799`) и не поддерживает второй канал — вне scope.

## Зависимости

- `none` — только существующие пакеты `websocket`, `framing`, `session`, `handshake`, `demux`, codegen.

## Требования

- RQ-001 ClientHello ДОЛЖЕН позволять вторичному каналу указать `session_id` первичного канала и факт вторичности; поля ДОЛЖНЫ быть необязательными и не ломать старый формат.
- RQ-002 Сервер ДОЛЖЕН принимать вторичный WS-канал и привязывать его к активной сессии по `session_id`; привязка ДОЛЖНА выполняться только при совпадении токена вторичного канала с токеном, под которым создана целевая сессия; при отсутствии активной сессии или несовпадении токена ДОЛЖЕН закрыть канал с ошибкой аутентификации.
- RQ-003 Клиент ДОЛЖЕН классифицировать исходящие TUN-пакеты по IP-протоколу: UDP → вторичный канал, остальные → первичный.
- RQ-004 Сервер ДОЛЖЕН классифицировать возвратные пакеты по IP-протоколу и писать их в соответствующий стрим сессии.
- RQ-005 При недоступности вторичного канала клиент ДОЛЖЕН продолжить работу на первичном канале со всем трафиком (фоллбэк без изменения конфигурации).
- RQ-006 Сервер ДОЛЖЕН буферизовать UDP-данные вторичного канала, поступившие раньше привязки первичного, на ограниченное время, затем сбросить их.
- RQ-007 Настройки обфускации (uTLS, padding, SNI) вторичного канала ДОЛЖНЫ быть идентичны первичному (консистентный DPI-fingerprint).
- RQ-008 Вторичный канал ДОЛЖЕН использовать тот же `sessionCipher` (крипто-материал сессии), что и первичный, деривированный от того же `CryptoSalt` и `session_id`; шифрование/дешифрование в обоих каналах ДОЛЖНО использовать общие ключи.
- RQ-009 Существующее поведение одиночного канала НЕ ДОЛЖНО измениться для клиентов, не поддерживающих второй канал.
- RQ-010 После изменений `go test -race ./...` для затронутых пакетов ДОЛЖЕН проходить.

## Вне scope

- QUIC-транспорт и QUIC-мультистрим — отдельная тема.
- SOCKS5 UDP ASSOCIATE (proxy-режим) — отдельная фича.
- Android-клиент (OkHttp WebSocket) — не поддерживает второй канал.
- Приоритизация внутри одного канала (drop-stale UDP) — альтернатива, а не часть этой фичи.
- Изменение фреймового формата `FrameTypeData` и схемы аутентификации.

## Критерии приемки

### AC-001 Вторичный канал привязывается к сессии по session_id

- Почему это важно: без привязки пакеты вторичного канала нельзя отнести к IP-пулу и возвратной маршрутизации; без проверки токена привязка открывает attach к чужой сессии.
- **Given** активная сессия клиента с `session_id` на сервере
- **When** клиент открывает второй WS и шлёт ClientHello с `session_id` первичного канала и тем же токеном
- **Then** сервер привязывает второй стрим к той же сессии, handshake успешен; вторичный канал с неверным токеном отклоняется
- Evidence: интеграционный тест: вторичный канал получает ServerHello; пакет, отправленный по вторичному каналу, попадает в TUN сервера с корректным source-IP клиента; канал с теми же `session_id`/только `session_id`, но другим токеном, закрывается с ошибкой аутентификации.

### AC-002 UDP вторичный, остальное первичный

- Почему это важно: это и есть изоляция VoIP-медиа от HoL общего потока.
- **Given** клиент с двумя установленными каналами в TUN-режиме
- **When** приложение отправляет UDP-пакет (RTP) и TCP-пакет одновременно
- **Then** UDP-пакет покидает клиент по вторичному каналу, TCP — по первичному
- Evidence: интеграционный тест на обеих сторонах регистрирует, в какой стрим попал каждый кадр; counters первичного и вторичного каналов соответствуют протоколу пакетов.

### AC-003 Возвратные пакеты пишутся в правильный стрим

- Почему это важно: без этого клиент не получит UDP-ответы в нужном канале.
- **Given** сессия с двумя каналами и активный UDP-обмен
- **When** сервер читает из TUN пакет с destination = IP клиента
- **Then** пакет уходит в стрим по своему протоколу (UDP → secondary, TCP → primary)
- Evidence: интеграционный тест проверяет, что UDP-ответ приходит клиенту по вторичному каналу и доставляется в TUN клиента.

### AC-004 Фоллбэк на одиночный канал

- Почему это важно: старый сервер/сеть не должны ломать существующих клиентов; падение вторичного канала посреди сессии не должно останавливать соединение.
- **Given** сервер, не поддерживающий вторичный канал (старая версия протокола), либо вторичный канал, упавший после установки
- **When** клиент пытается поднять второй канал и получает ошибку/закрытие, либо теряет установленный вторичный канал
- **Then** клиент продолжает работать на первичном канале со всем трафиком (включая UDP) до переподключения вторичного канала
- Evidence: интеграционный тест: вторичный handshake завершился ошибкой, данные по первичному каналу проходят без потерь; при закрытии вторичного канала после установки UDP-трафик продолжает доставляться по первичному до повторного привязывания.

### AC-005 Буфер вторичного канала до привязки первичного

- Почему это важно: защита от гонки поднятия каналов, чтобы UDP-медиа не терялось в первые мгновения.
- **Given** вторичный канал привязался к сессии раньше, чем привязан первичный
- **When** по вторичному каналу приходят UDP-данные
- **Then** сервер держит их в буфере ограниченное время (порядка сотен мс); после привязки первичного — сбрасывает в TUN, при превышении — дропает
- Evidence: unit-тест на серверной логике: данные не пишутся в TUN до появления первичного канала, после — пишутся; по истечении буфера пакеты отбрасываются без паники/утечки.

### AC-006 Идентичная обфускация и крипто-материал обоих каналов

- Почему это важно: расхождение fingerprint'ов двух соединений одного клиента — след для DPI; расхождение cipher'ов ломает шифрование данных.
- **Given** конфигурация с включённой обфускацией (uTLS, padding) и app-layer crypto
- **When** клиент поднимает оба канала
- **Then** оба канала используют идентичные uTLS-fingerprint, padding-настройки и SNI, а также один общий `sessionCipher` (деривированный от одного `CryptoSalt` и `session_id`)
- Evidence: code review + unit-тест: оба стрима создаются одним `WSConfig`-источником; проверка, что `PaddingEnabled`/`UTLS` не различаются; unit-тест шифрования: пакет, зашифрованный клиентом на вторичном канале, дешифруется сервером тем же ключом сессии.

### AC-007 Обратная совместимость протокола

- Почему это важно: старые клиенты и серверы должны продолжать работать без обновления.
- **Given** старый клиент с одиночным каналом и новый сервер
- **When** старый клиент проходит handshake (без новых полей)
- **Then** сервер обслуживает его как одиночный канал
- Evidence: `go test` существующего handshake codec: декодирование hello без новых полей эквивалентно старому формату.

### AC-008 Нет регрессии существующих тестов

- Почему это важно: фича не должна ломать текущее поведение.
- **Given** затронутые пакеты (`transport/websocket`, `protocol/handshake`, `tunnel`, `bootstrap/*`)
- **When** прогоняются тесты
- **Then** все существующие тесты проходят, `go vet` чист
- Evidence: `go test -race ./src/internal/... ./src/integration/...` PASS и чистый `go vet`.

## Допущения

- Классификация по IP-протоколу достаточна: у VoIP-медиа транспортом является UDP; TCP-трафик не является real-time и переживает HoL.
- Разделение по протоколу не требует новых типов фреймов — только маршрутизации по стримам.
- Вторичный канал использует тот же endpoint/TLS/WS-стек, что и первичный — консистентный fingerprint.
- App-layer crypto на вторичном канале пере-деривирует тот же `sessionCipher` из `masterKey`, `CryptoSalt` сессии и `session_id` — ключи общие для обоих каналов.
- Привязка вторичного канала выполняет полную аутентификацию (токен) и проверку принадлежности `session_id` сессии этого токена.
- Буфер вторичного канала ограничен по времени (сотни мс) и по количеству пакетов — real-time предпочитает свежий пакет старому.
- Сервер может не знать о вторичном канале заранее — привязка идёт по `session_id` из hello.

## Критерии успеха

- SC-001 Интеграционный тест двухканальной сессии: UDP-медиа проходит при искусственной блокировке первичного канала без ожидания ретрансмиссий (джиттер UDP < 100 мс при задержке TCP-потока).
- SC-002 Регрессия: `go test -race ./src/internal/... ./src/integration/...` PASS, `go vet` чист.

## Краевые случаи

- Вторичный канал пришёл раньше первичного — буфер с ограничением по времени, затем дроп (AC-005).
- Вторичный канал переподключается после обрыва — повторная привязка по `session_id`.
- Сессия первичного канала завершена, а вторичный жив — вторичный канал закрывается сервером.
- Один `session_id` с несколькими вторичными каналами — привязывается первый, последующие отклоняются.
- Клиент без поддержки фичи на старом сервере — обычный одиночный канал (AC-004, AC-007).

## Открытые вопросы

- `none` — развилки (единый session_id, разделение по протоколу, буфер) закрыты на этапе дизайна.
