# QUIC Datagrams — unreliable-транспорт для real-time UDP

## Scope Snapshot

- In scope: передача real-time UDP (игры/VoIP) как unreliable QUIC datagrams поверх существующего QUIC-транспорта, чтобы убрать ретрансмиссию и head-of-line blocking; аддитивное согласование возможности и fallback на stream.
- Out of scope: работа по padding/MTU (фича `game-latency`), FEC/повторы на уровне приложения, Android-QUIC, изменение схемы аутентификации, приоритизация датаграмм.

## Цель

Пользователь Go-клиента на QUIC-транспорте получает отсутствие ретрансмит-сталов: потеря одной датаграммы не блокирует остальной трафик и не вызывает повторов, а TCP/control идут по stream как раньше. Успех виден по стабильной задержке stream-трафика при потерях датаграмм и по неизменной работе WS/Android.

## Основной сценарий

1. Стартовая точка: Go-клиент с `transport: quic`, идёт real-time UDP.
2. Основное действие: обе стороны объявляют datagram-возможность; UDP-пакеты идут datagram-фреймами, TCP/control — stream.
3. Результат: потеря датаграммы не блокирует stream и не задерживает другие датаграммы.
4. Ошибка/fallback: возможность не совпала или транспорт не QUIC → весь UDP идёт stream, как раньше.

## User Stories

- P1 Story: как игрок, я хочу, чтобы потеря части пакетов не вызывала «залипаний» и задержек остального трафика.
- P2 Story: как инженер, я хочу включать это безопасно: старые пары клиент/сервер и Android продолжают работать.

## MVP Slice

Наименьший срез: UDP идёт datagram'ами при обоюдной поддержке, stream не блокируется, есть fallback — закрывает AC-001, AC-002, AC-003, AC-004.

## First Deployable Outcome

Go-клиент и сервер, при которых игровой UDP передаётся datagram-путём при обоюдной поддержке, а потеря датаграмм не ставит stream-трафик; при несовместимости — прежний stream-режим. Проверяется интеграционным тестом с искусственной потерей.

## Scope

- QUIC-транспорт: отправка/приём unreliable datagrams.
- Аддитивное объявление datagram-возможности в handshake.
- Клиентская маршрутизация: real-time UDP → datagram, остальное → stream.
- Серверное сопряжение и fallback к stream.

## Контекст

- quic-go v0.50.0 поддерживает datagrams (`EnableDatagrams`/`SendDatagram`/`ReceiveDatagram`); сейчас используется одна stream на сессию.
- Android не использует QUIC (OkHttp WebSocket) — datagram-путь его не касается.
- Сервер обслуживает TCP/WS и (при `transport: quic`) QUIC одновременно, поэтому WS-путь обязан остаться неизменным.
- Расширения протокола ранее делались аддитивно тегами (batching, dual-channel) — этот же принцип сохраняется.

## Зависимости

- Существующий QUIC-транспорт и quic-go v0.50.0 datagram API (жёсткое ограничение стека репозитория).
- Совместимость со существующим handshake (добавление опционального тега).

## Требования

- RQ-001 Real-time UDP ДОЛЖЕН передаваться unreliable datagram'ами поверх QUIC: без ретрансмиссии и без блокировки другого трафика.
- RQ-002 Datagram-возможность ДОЛЖНА согласовываться в handshake и включаться только при обоюдной поддержке и QUIC-транспорте.
- RQ-003 TCP/control и прочий не-UDP трафик ДОЛЖНЫ идти по stream без изменений.
- RQ-004 Fallback: при несовместимости или не-QUIC транспорте поведение прежнее (UDP по stream), без ошибок.
- RQ-005 WS-путь и Android-клиент НЕ ДОЛЖНЫ затрагиваться.
- RQ-006 Потеря/дубликаты/перестановка датаграмм ДОЛЖНЫ быть допустимы без разрыва сессии.

## Вне scope

- Padding/MTU-тюнинг и снятие задержки агрегации — фича `game-latency`.
- FEC, прикладные повторы, retransmission-политики поверх datagram.
- QUIC на Android и любые изменения Android-клиента.
- Маркировка DSCP/управление очередями.
- Изменение схемы аутентификации и формата stream-фреймов.

## Критерии приемки

### AC-001 Real-time UDP идёт datagram'ами

- Почему это важно: это и есть снятие ретрансмит-сталов.
- **Given** Go-клиент с `transport: quic` и сервер с поддержкой datagrams, возможность согласована
- **When** клиент отправляет real-time UDP
- **Then** пакеты уходят datagram-путём, а не stream
- Evidence: интеграционный тест: UDP доставлен, счётчик принятых/отправленных датаграмм > 0, stream-счётчик для этого потока не растёт.

### AC-002 Потеря датаграммы не блокирует stream

- Почему это важно: именно HOL-блокировка делает игры/медиа неиграбельными при потерях.
- **Given** активная сессия с datagrams и параллельным TCP-потоком
- **When** часть датаграмм теряется
- **Then** задержка TCP-потока p99 не превышает базовый RTT + 50 мс, и потерянные датаграммы не ретрансмитятся
- Evidence: тест с искусственной потерей датаграмм; измерение задержки stream и отсутствие повторов в счётчиках.

### AC-003 Согласование возможности и fallback

- Почему это важно: старые пары не должны ломаться.
- **Given** сервер без поддержки datagrams или не-QUIC транспорт
- **When** клиент подключается
- **Then** datagram-режим не включается, весь UDP идёт stream, без ошибок
- Evidence: интеграционный тест обеих сторон; отсутствие datagram-трафика и успешная доставка UDP по stream.

### AC-004 WS/Android не затронуты

- Почему это важно: нельзя ломать существующий WS-путь и Android.
- **Given** WS/OkHttp-клиент (Android) подключается к тому же серверу
- **When** идёт смешанный трафик
- **Then** поведение идентично прежнему, сервер обслуживает WS как раньше
- Evidence: существующие WS-тесты зелёные; smoke-подключение по WS без изменений.

## Допущения

- Игровой/VoIP-трафик — UDP, для которого потеря и перестановка допустимы (приложение восстанавливается само).
- Размер датаграммы ограничен (предел datagram frame); пакеты больше отправляются не датаграммами.
- Потеря датаграммы не должна завершать сессию.
- Capability-тег аддитивен: старые парсеры его игнорируют, совместимость сохраняется.

## Критерии успеха

- SC-001 При искусственной потере 5% датаграмм задержка stream-трафика p99 растёт не более чем на 50 мс от базового RTT.
- SC-002 Нет регресса пропускной способности и стабильности: soak/speedtest-гейты зелёные.
- SC-003 Ноль ретрансмитов на датаграммном пути по счётчикам.

## Краевые случаи

- UDP-пакет больше предела datagram frame → что применяем: дроп, stream-fallback или прикладная фрагментация.
- Переподключение/миграция QUIC и повторное согласование возможности.
- Смешанный UDP (DNS/53) наряду с игровым — не должен терять надёжность.
- Контрольные и keepalive-фреймы не должны становиться датаграммами.
- Старый клиент + новый сервер и новый клиент + старый сервер.

## Открытые вопросы

- Политика для UDP-пакетов больше предела datagram frame: дроп, stream-fallback или прикладная фрагментация?
- Нужен ли reliable-режим для части UDP (например DNS), или весь UDP идёт unreliable?
- Порядок датаграмм не гарантируется — подтверждаем, что игровые/VoIP-приложения это переживают без деградации.
